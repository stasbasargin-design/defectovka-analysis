# Предметные правила и контракты (проект требований)

Требования для реализации и проверки, а не подтверждение того, что они уже воплощены в рабочем коде.

1. Входной JSON от 1С не менять без отдельного согласования.
2. Сохранить существующий briefing; минимально расширить исходящий JSON привязкой `works` и `parts` к конкретным дефектам.
3. Раздельно классифицировать `reason`, `defect`, `recommendation`; ранее согласованные работы не добавлять повторно.
4. Связанные работы определять только через выбранную основную работу. Запчасти подбирать только под выбранные работы.
5. Проверять марку, модель, вариант комплектации и подтверждённый состав агрегатов; VIN учитывать при совпадении подтверждённой комплектации.
6. При повторе детали в одном дефекте суммировать количество. Не смешивать количества между разными дефектами.
7. ТО определять по регламентному шагу с допуском ±1000 км; неоднозначные случаи отправлять на проверку.
8. Исключать запрещённые работы и неподтверждённые похожие позиции; сомнительные кандидаты помечать `needs_review`.
9. Применять позитивные и негативные тесты: не только наличие нужной позиции, но и отсутствие лишних.
10. Проверять соответствие исходящего JSON контракту 1С до внедрения.

## Ограничения версии 0

Нет актуального экспорта реального n8n workflow, примеров полноценного входящего/исходящего JSON и тестовой PostgreSQL. Правила в `src/` — демонстрационные, а не боевой алгоритм.
