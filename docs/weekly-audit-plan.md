# Еженедельный аудит АвтоКП — план реализации

Дата фиксации: 2026-11-20. Статус: **план; к боевым PostgreSQL и n8n пока не подключён**.

## Назначение и границы

Раз в неделю n8n под отдельным пользователем выполняет read-only анализ реальных данных АвтоКП, КП, истории удалений, закрытых ЗН, работ и ЗЧ. SQL формирует воспроизводимые показатели, ИИ предлагает объяснения и исправления с привязкой к документам. На email уходит сводка и XLSX с доказательствами. Боевую логику подбора запрещено менять автоматически.

GitHub — источник версий и тестов. Учётная запись n8n — только исполнитель: экспорт workflow в GitHub, секреты и credentials остаются в n8n. Доступ сервисному пользователю БД — с минимумом полномочий; при необходимости запись истории аудитов в отдельную схему и под отдельной ролью.

## Этапы и критерии готовности

### 0. Инвентаризация (первая задача)
- Проверить существующие файлы, тесты и workflow в GitHub, не заменяя текущие компоненты.
- Зафиксировать контракты: вход/выход JSON, блоки дефектов, briefing, связи works/parts, GUID документов.
- Проверить реальную схему PostgreSQL и таблицы: `bot_ea_АвтоКП`, история удалений, `repair_order_*`, `ref_works`, `ref_parts`, `linked_works`, `linked_parts`.
- Составить карту: автоКП → КП → удаление/добавление → закрытый ЗН, со связью до строк.
- Найти дубли выгрузок, незакрытые ЗН, несопоставимые документы и интервалы задержки.
**Готово, когда:** на контрольной выборке все метрики можно проследить до исходной записи; неизвестные случаи отмечены отдельно.

### 1. SQL-слой и достоверные метрики
- Когорта А: АвтоКП за прошедшую неделю; когорта Б: ЗН, закрытые за неделю (не смешивать).
- Измерять принятие/удаление/ручное добавление работ и ЗЧ, повторы, несовместимые агрегаты/комплектации, совпадения по коду и артикулу.
- Стратифицировать по БЕ, мастеру, марке/модели/комплектации, группе работ, версии алгоритма.
- Удаление не считать доказательством ошибки: отказ клиента, предыдущие согласования, аналоги и ручные ошибки требуют раздельной классификации.
- Метрики сопровождать числителями, знаменателями, покрытием сопоставления и ссылками на документы.
**Готово, когда:** SQL-тесты и сверка с выборкой 1С подтверждают показатели.

### 2. Рекомендательный аудитор
- ИИ (планируется Astra) получает только результаты SQL и минимально необходимые обезличенные свидетельства.
- На каждую рекомендацию: тип, причина-гипотеза, доказательства, затронутые коды работ/артикулы, число случаев, уверенность, влияние, риск, тест.
- Низкая уверенность → очередь ручной проверки; рекомендация сама по себе не изменяет `linked_works` или `linked_parts`.
- Строго проверять формат JSON рекомендаций и отсутствие вымышленных номеров документов.
**Готово, когда:** рекомендации воспроизводимы и каждая имеет подтверждённую связь с данными.

### 3. Отчётность и расписание
- Короткое HTML-письмо + подробный XLSX: недельные метрики, сравнение с предыдущим периодом, проблемные позиции, примеры и рекомендации.
- Экспорт n8n workflow без учётных данных в GitHub; импорт в отдельный аккаунт n8n и ручная привязка credential IDs.
- Расписание: понедельник, 09:00 Asia/Yekaterinburg (предложение, согласовать).
- Защита от повторной рассылки (период + run_id); алерты о неполной выгрузке, несопоставленных данных, ошибках SQL/ИИ/email.
- Проверить отправку тестового письма и повторный прогон без дублей.
**Готово, когда:** успешен end-to-end запуск с проверенным содержимым письма.

### 4. Полуавтоматическое улучшение
- Из рекомендаций формировать изменения только в отдельной ветке / Pull Request.
- Перед слиянием: регрессионные тесты дефектовок и JSON, проверка по моделям/комплектациям/агрегатам, примеры до/после, план отката.
- После согласования изменения применяются в целевой среде; разницу качества отслеживать в следующих отчётах.
- Автоматическую запись правил в продуктив **не включать** без отдельного решения.
**Готово, когда:** одна проверенная рекомендация прошла цикл аудит → PR → тесты → одобрение → ручной релиз → повторная оценка.

## Что может делать ассистент, что требует доступа
**Самостоятельно через GitHub:** изучать/изменять код и тесты, разрабатывать SQL и n8n JSON, писать документацию и CI, готовить PR и анализировать тестовые выгрузки.

**Зависит от инфраструктуры:** чтение боевой PostgreSQL, установка/импорт workflow в аккаунт другого пользователя, создание credentials и отправка email. Для этого нужен разрешённый доступ или действия администратора в n8n; пароли в репозиторий и в чат не помещать.

**Решение владельца:** адрес письма, точное расписание и утверждение боевых изменений.
